# 格式化字符串

## 先确定调用形态

```c
printf(user);          // user 同时控制格式串
printf("%s", user);   // 不是格式串漏洞
snprintf(dst, n, user);
```

确认：

- 格式串位于栈、堆还是全局区；
- 调用是 `printf`、`fprintf`、`sprintf`、`snprintf` 还是宽字符版本；
- 输出是否经过缓冲、长度限制或二次编码；
- `_FORTIFY_SOURCE`、只读格式串检查和禁用 `%n` 的运行库策略。

## 泄漏

常用转换：

| 格式 | 效果 | 风险 |
|---|---|---|
| `%p` | 把参数解释成指针打印 | `(nil)`、宽度和前缀会影响解析 |
| `%x`/`%lx`/`%llx` | 按整数宽度打印 | 长度修饰符必须匹配 ABI |
| `%s` | 把参数解释成地址并持续解引用 | 地址不可读或缺 NUL 会崩溃 |
| `%c` | 消耗参数并输出一个字符 | 常用于累计输出长度 |
| `%n` 家族 | 写入当前已输出字符数 | 见下一节 |

位置参数便于稳定访问：

```text
%7$p
%12$s
%15$hn
```

同一格式串中不要随意混用位置参数与非位置参数。先用短探针找 index，再把目标地址放进输入，确认它在参数区的实际位置。

当输入同时承载格式串和伪参数时，常见布局是：

```text
[format bytes][NUL][alignment padding][target pointers]
```

NUL 只终止格式串解析，不会阻止后方地址已经存在于栈参数区；但地址是否能成为第 `N` 个参数完全由调用点 ABI、输入落点和对齐决定。用 GDB 看实际地址，不要从 payload 长度心算 index。

## `%n` 写入

| 格式 | 写入类型/典型宽度 |
|---|---|
| `%hhn` | 1 字节 |
| `%hn` | 2 字节 |
| `%n` | `int`，通常 4 字节 |
| `%ln` | `long`，x86-64 通常 8 字节 |
| `%lln` | `long long`，通常 8 字节 |

写入值是**到 `%n` 被处理时已经产生的输出字符数**，不包括尚未执行的后续转换。终端上看不见的 padding 也计数，`snprintf` 截断时的语义也要按目标实现验证。

分字节/半字写的一般步骤：

1. 把目标拆成 `hhn` 或 `hn` 单元。
2. 按模 `0x100`/`0x10000` 的目标值排序，减少回绕。
3. 计算已经输出的前缀长度和每段 padding。
4. 确认地址参数没有被格式串中的其他 `*`、宽度或转换提前消耗。

pwntools 可以生成基础 payload：

```python
writes = {
    target: value,
}
payload = fmtstr_payload(offset, writes, write_size="short")
```

自动生成器不知道目标对坏字符、最大长度、NUL 截断和多轮输入的限制，必须检查生成结果。

## 二重指针与分阶段改写

格式化字符串经常不能直接把任意地址作为参数，但栈上可能已有：

```text
参数 A → 栈槽 B → 栈槽 C/返回地址
```

可以先用较低位的 `%hhn/%hn` 改写 A 指向的栈槽，让它成为目标指针；下一轮再通过 B 写最终地址。这就是旧笔记所说的“主要看二重指针”，但每一步都要满足：

- 被改写指针的高位保持正确；
- ASLR 下页内偏移或低字节可预测；
- 每轮函数返回前不会覆盖这个栈槽；
- 输出长度和输入 NUL 不破坏下一阶段。

栈溢出也可能先修改参数区的指针，再由后续安全格式串完成任意读写；应同时检查调用前后的栈布局。

### 同一次调用内改指针再使用

若格式串使用连续的非位置参数，前面的 `%hhn/%hn` 有时能改写后面尚未取用的栈参数指针，后续转换再经修改后的指针读写。这能把“需要两轮”的指针重定向压进一次 `printf`，但依赖目标实现何时读取参数。

位置参数格式串通常会先扫描格式、建立参数类型表，再预取参数值；这时前半段改了栈槽，后半段的 `%N$n` 还可能用已缓存的旧值。是否可行必须在目标 `vfprintf` 上断到参数获取点验证，不能只看栈内存已经变化。

## 只有一次格式串调用时争取重新进入

一次 `%n` 若不足以完成最终写，可以优先把它用于获得第二轮输入，例如改 saved return address、合法 callback，或在正常退出会消费且当前确实可写时修改 `.fini_array`/loader fini 状态，使程序重新进入 `main` 或输入函数。

`.fini_array` 常位于 GNU_RELRO，启动后未必可写；执行顺序通常反向遍历，且是否存在旧式 `__libc_csu_fini` 循环取决于链接产物。利用它做无限 re-entry 或把数组附近当 fake stack，都必须检查真实 mapping、退出 API、当前 `rbp/rsp` 和每轮析构副作用。[Ltfall 的一次格式串与 fini-array 笔记](https://ltfa1l.top/2023/12/28/system/tricks/tricks/)提供了旧题实例，但固定数组下标与 CSU 模板不能直接复用。

## 无直接输出时的 oracle

格式化结果被丢弃或只返回长度时，还能找一位反馈：进程是否崩溃、返回值是否跨过分支、连接是否关闭、某个写入是否在下一轮可见。`%s` 读到可访问/不可访问页、`%n` 改写长度或状态字段，都可能把秘密 bit 转成不同外部行为。

[Blind Format String Attacks](https://eudl.eu/pdf/10.1007/978-3-319-23802-9_23)给出了无回显和堆上格式串场景的方法论。CTF 中应先测 oracle 的误判率、进程重启模型和查询预算，再决定逐 byte、二分还是页级探测。

## sink 前存在输入变换

若用户输入在到达 `printf` 前经过 ROT13、大小写转换、URL/base64 解码或字符替换，应写成：

```text
memory_format = T(network_input)
```

先为目标格式串和后置地址求 `T` 的逆像，再检查变换是否会改变 `%`、`$`、数字、NUL 和地址 bytes。[SunshineCTF 2018 Rot13](https://ctftime.org/writeup/9549)就是先求 ROT13 逆像，再使用格式串原语；不能直接把网络 payload 当成内存中的格式串。

## 格式化函数自身的 allocator side effect

某些旧 glibc 的 `vfprintf` 会因极大字段宽度申请临时缓冲。它可能给堆布局提供额外的隐式 `malloc/free`，也可能只制造巨量输出和阻塞；版本条件和验证方法见 [`INPUT_AND_IO.md`](./INPUT_AND_IO.md#历史-printf-大字段宽度的-allocator-side-effect)。

## 调试清单

```gdb
# 停到真正解析格式串的位置
b printf
b __vfprintf_internal

# x86-64 SysV: 前六个参数寄存器 + 当前栈
info registers rdi rsi rdx rcx r8 r9 rsp
x/40gx $rsp
x/s $rdi
```

Pwndbg/Pwngdb 的 `fmtarg` 只能辅助找索引。最终以目标调用点的寄存器保存区、栈参数和格式串位置为准。

## 快速故障定位

- 泄漏少一字节：检查 `%s` 是否被 NUL、换行或菜单读长截断。
- 写入差一个固定值：重算格式串前缀已经输出的字符数。
- 第二次写崩溃：第一轮可能只改了低位，指针高位或对齐不成立。
- 同次调用改指针无效：位置参数可能已经被预取；改用非位置参数顺序消费，或拆成两轮。
- 本地成功远程失败：核对 libc Build ID、locale、缓冲方式和参数 index。
- `fmtstr_payload` 太长：尝试分轮写、改用 `hhn`、复用已有指针或先做 stack pivot。
